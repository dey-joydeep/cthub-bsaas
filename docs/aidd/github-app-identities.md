## Runtime boundary

The private keys are held outside this repository. Never copy a key or token into source, a PR, an AIDD checkpoint, or chat. The deployed broker keeps each role's key separately, mints short-lived installation tokens limited to `cthub-bsaas` and the operation's minimum permissions, and binds each grant to an exact action and role-specific executor. Separate bot names provide attribution; independent PO and QA evidence still has to be checked.

The read-only verifier accepts a role and a path to that App's private key: `node scripts/aidd/verify-github-app-installation.mjs <po|qa|dev> <key-path>`. Run it only from an operator-controlled environment. It signs a short-lived App JWT in memory, checks the App ID, slug, installation ID, selected-repository scope, repository installation, and exact permissions, and prints no key or token. It does not mint an installation token or perform a GitHub write. The path is supplied at runtime so a new machine may use a different protected location. Never paste the key or an unredacted MCP/server listing into a chat or log.

For multi-machine recovery, store the keys in a backed-up secrets vault. A OneDrive Personal Vault may serve as the operator's backup if it is unlocked and verified. Do not keep a local copy readable to the same Windows user as desktop agents: those agents can mint installation tokens directly and bypass the hosted broker. Keep the Vault locked during agent work; unlock it only for operator-controlled rotation or re-provisioning. A separate OS identity with restricted filesystem access is required for any persistent local key cache. Do not put private keys in a repository, submodule, project environment file, or agent-visible workspace.

The hosted broker runs outside the agent's process and filesystem access. Its operation allowlist covers PO issues, QA PR review comments, and Dev task-branch commits and PR creation. It rejects main/release pushes, workflow edits unless separately granted, cross-repository targets, and role changes requested only through an argument. It mints repository- and permission-scoped installation tokens for one operation and keeps keys and tokens out of agent output. The grant binds the action, issue or PR, target, executor, and creator; after success, D1 retains the actor and result while clearing the grant input. The resulting GitHub artifact carries its own issue, PR, or branch context. An agent receives only the capability for its assigned operation, not the private key or a general installation token. QA check-run authorship alone is not independent QA evidence.

The deployed contract requires one owner-created task mandate with a fixed outcome, issue, task branch, allowed file paths, per-action issue limits, and expiry. The owner uses the Access-protected `/owner` page to review the exact scope and enter a fresh authenticator code from a separate device; the same API supports direct calls. An uncreated issue can be opened once by PO; its number is then bound to the mandate. A role-specific Access caller can request a single-use grant only while the mandate is active and within its quota. Revocation prevents new and unclaimed actions; an already running GitHub write may still finish and requires reconciliation. The broker verifies the GitHub actor as `shearflow-<role>[bot]` before returning success. The desktop/CLI client in `scripts/aidd/broker-client.mjs` verifies its Access principal and result actor. Live end-to-end mandate evidence remains pending.

Once activated, PO, QA, and Dev bot writes must use the broker. If a role token or broker is unavailable, mark the operation blocked; never silently fall back to the owner's `gh` credential. The coordinator may still use the separately authorized owner credential for GitHub Project fields, which the PO App cannot access. Bot attribution is not independent review: record the actual reviewer, evidence, and head commit. Service tokens stored under the same OS account do not technically isolate roles from each other. Do not infer names such as `cthub-bsaas-dev[bot]`; the three exact App names are listed above.

The current user-owned [cthub Project](https://github.com/users/dey-joydeep/projects/1) is outside the PO App installation token's scope. The coordinator uses a separately authorized user credential for Project fields until a different board ownership or credential design is approved.

The earlier GitHub Actions dispatch prototype was removed because its protected-environment design was unavailable under the repository's former private Free-plan configuration. The hosted broker replaced that prototype. It is enabled, but routine bot writes require an owner-created task mandate and successful live role probes.
