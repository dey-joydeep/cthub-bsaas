GitHub Apps can act as distinct bot accounts on GitHub Free, including in this private repository. The Dev App has Contents write for HTTPS Git pushes and Pull requests write for PR operations. The user also granted Workflows write so Dev can make authorized changes to `.github/workflows/**`; this permission does not authorize every Dev task to change CI or deployment workflows. ## Runtime boundary

The private keys are held outside this repository. Never copy a key or token into source, a PR, an AIDD checkpoint, or chat. A future runner must keep each role's key separately, mint short-lived installation tokens limited to `cthub-bsaas` and the operation's minimum permissions, and verify the App and installation before acting. It must not allow an agent to select a different role by simply changing an argument. Separate bot names provide attribution; independent PO and QA evidence still has to be checked.

The read-only verifier accepts a role and a path to that App's private key: `node scripts/aidd/verify-github-app-installation.mjs <po|qa|dev> <key-path>`. Run it only from an operator-controlled environment. It signs a short-lived App JWT in memory, checks the App ID, slug, installation ID, selected-repository scope, repository installation, and exact permissions, and prints no key or token. It does not mint an installation token or perform a GitHub write. The path is supplied at runtime so a new machine may use a different protected location. Never paste the key or an unredacted MCP/server listing into a chat or log.

For multi-machine recovery, store the keys in a backed-up secrets vault. A OneDrive Personal Vault may serve as the operator's backup if it is unlocked and verified. Do not keep a local copy readable to the same Windows user as desktop agents: those agents can mint installation tokens directly and bypass the hosted broker. Keep the Vault locked during agent work; unlock it only for operator-controlled rotation or re-provisioning. A separate OS identity with restricted filesystem access is required for any persistent local key cache. Do not put private keys in a repository, submodule, project environment file, or agent-visible workspace.

Before activating bot writes, run a separate trusted broker outside the agent's process and filesystem access. Bind each credential to an explicit operation allowlist: PO issues; QA review comments and QA evidence; Dev task-branch pushes and PRs. The broker must reject main/release pushes, workflow edits unless separately authorized, cross-repository targets, and role changes requested only through an argument. It should mint repository- and permission-scoped installation tokens for one operation, keep keys and tokens out of agent output, and record the actor, task issue, target, and resulting URL/SHA. An agent must receive only the capability for its assigned operation, not the private key or a general installation token. QA check-run authorship alone is not independent QA evidence.

The current user-owned [cthub Project](https://github.com/users/dey-joydeep/projects/1) is outside the PO App installation token's scope. The coordinator uses a separately authorized user credential for Project fields until a different board ownership or credential design is approved.

The earlier GitHub Actions dispatch prototype was removed because its protected-environment design was unavailable on the current private Free repository and could mislead agents into treating the Apps as active. A Free-compatible trusted runner is a separate implementation task; no private key is needed merely to keep these App registrations installed.
