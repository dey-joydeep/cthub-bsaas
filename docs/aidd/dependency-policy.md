# Dependency Change Policy

**Status:** Current AIDD policy

Use this policy for root and workspace npm manifests, the lockfile, and project npm configuration. The dependency owner is accountable for the package choice and the resulting tree; independent Codex review still applies to the PR. A security-sensitive package or install script receives Codex security review.

## Adding, removing, and updating packages

1. Identify the owning workspace, need, license, maintenance status, and the smallest compatible version change. Install in that workspace when possible. Do not add a package to the root merely to make a sibling import resolve.
2. Use the repository Node/npm versions. Resolve a targeted change with `npm install <name>@<version> --workspace <workspace> --package-lock-only --ignore-scripts` or remove it with `npm uninstall <name> --workspace <workspace> --ignore-scripts`. Inspect the resulting manifest and lockfile, including transitive changes and every newly introduced or upgraded install-time script. Only then install the reviewed tree with scripts disabled (`npm ci --ignore-scripts`); run required setup explicitly after review, such as the version check, Husky installation for local development, and Prisma client generation. If a native package needs rebuilding, inspect that package's script first and rebuild it in an environment without privileged credentials. Commit the manifest and lockfile together. Never run unreviewed dependency scripts on a machine with privileged credentials.
3. In the PR body, set `Dependency owner: <person or agent owner>` and add one `- <package>: <specific reason>` line per changed direct dependency. When the lockfile introduces or upgrades packages with install scripts, inspect them and list every reported lockfile path after `Install scripts reviewed:`. Registry packages must resolve from the approved HTTPS npm registry with a SHA-512 integrity hash; local links must point to declared workspaces. A different package source requires a reviewed policy change before installation. Cite the assessment or finding disposition when the change is security-sensitive.
4. Run `npm run deps:policy` locally. CI checks policy and PR evidence before installation, uses `npm ci --ignore-scripts` followed by explicit required setup, and runs `npm audit --audit-level=high` when the dependency lockfile changes. Resolve high or critical findings before merge. A risk exception requires a tracked, dated, human-owned decision and a separately reviewed gate change; a note in the PR alone cannot make a failing audit pass. The manually dispatched full audit remains available. The current tree has high and critical audit findings, so a lockfile-changing PR will fail this gate until they are remediated or a narrowly reviewed baseline mechanism is implemented.

A successful scripts-disabled install is not proof that native tools work. Fresh worktree setup and CI run `scripts/aidd/smoke-installed-toolchain.mjs` to exercise Nx, SWC, and esbuild; CI also generates and checks Prisma Client. If a clean install fails this smoke check, inspect the failing package's install script and its pinned lockfile version. Approve a narrow package-specific rebuild only after review, or revise the install policy with an explicit allowlist and a clean-install test. Do not remove the smoke check or enable all install scripts merely to make a build pass.

`npm run deps:check` is read-only and can report outdated packages. Update one deliberate package set at a time. `npm audit fix` and bulk update commands are not automatic remediation steps; inspect a dry run and apply a targeted version change through the normal PR path.

`npm prune` is allowed for local cleanup after confirming the active workspace and Git status. It is not an approval to remove declared dependencies. If it changes a tracked manifest or lockfile, review that diff through the same dependency process. Use `npm ci` for a clean reproducible install in CI and verification.

## Forbidden dependency bypasses

Do not use `--legacy-peer-deps`, `--force` or `-f` on dependency changes, `--package-lock=false` or `--no-package-lock`, or `--save=false` or `--no-save` when adding or removing a declared project dependency. The equivalent project `.npmrc` settings are forbidden. The root `.npmrc` requires engine compatibility, peer resolution, a lockfile, TLS verification, and the official npm registry. A project or scoped registry override needs a reviewed policy change before use. Resolve peer and engine conflicts instead of bypassing them.

`--ignore-scripts` and `--no-audit` are allowed for a deliberately scripts-disabled install or a pipeline that performs an explicit later audit and required setup. Persistent `audit=false` in project npm configuration is forbidden. `--omit=dev` is allowed for a production install, not as evidence that the full test toolchain passed. Do not lower a required audit threshold to make a finding disappear. A local or agent npm setting cannot be proven by a repository file scan; the owner checks the effective settings and CI uses a clean runner.

Local hooks give fast feedback but are bypassable. CI checks the committed files. Until private-repository branch protection is enabled, the release agent must report no-go when these checks fail, and the human owner must withhold merge authorization.
